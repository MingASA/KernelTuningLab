# Codex 任务：搭建 Kernel Tuning Research Lab v0.1

## 项目背景

我们正在研究“面向硬件特性的算子参数寻优智能体”，核心涉及两个层次：

- L2：给定 Kernel 实现、硬件与输入 Shape，在有限真实测量预算下找到高性能参数配置。
- L3：给定 Shape 分布与有限编译变体预算 K，选择一组配置及其分派函数，使整体期望执行时间尽可能低。

研究尤其关注新 GPU 上的低成本迁移，以及 AI 能否通过历史实验学习或生成可复用的配置选择策略、搜索算法，而非每次调用 LLM 重新调优。

你的任务是建设一个**长期可扩展、实验可复现、便于 AI Agent 自主研究的基础平台**，不是完成一次算子调优。

请先检查现有仓库并尽量复用已有实现。若没有合适的项目结构，可以创建 `kernel_tuning_lab/` 独立模块。

## 一、任务要求

### 1. 统一数据模型和配置空间

设计 Python 数据模型：

- `HardwareSpec`：GPU 型号、架构、SM、SMEM、寄存器、理论算力、带宽、缓存、支持的硬件特性等。
- `OperatorSpec`：算子类别、Kernel 实现、精度、参数定义、正确性基线。
- `ShapeSpec`：M/N/K、Batch、SeqLen 等具体算子参数。
- `KernelConfig`：tile、warps、stages、swizzle、split-K、cluster 等可扩展配置。
- `MeasurementRecord`：硬件、shape、config、正确性、编译时间、运行时间分布、失败原因、环境元数据等。
- `WorkloadDistribution`：一组带权重的 Shape。
- `SearchBudget`：最大测试次数与最大实际耗时。

必须区分配置无效、编译失败、正确性失败和真实性能较差。不同算子和 GPU 可以拥有不同配置空间和合法性条件。

实验结果存储使用 SQLite 或 Parquet/JSONL，提供规范化的数据导入导出与去重功能。

### 2. 实验执行与数据收集框架

建立统一 Benchmark Runner：

- 自动生成候选配置与进行合法性检查。
- 编译 Kernel，进行正确性验证和性能测量。
- 分别记录编译耗时与运行耗时。
- 记录 warmup、测量次数、分位数、测量模式、环境版本、GPU 信息。
- 支持断点续跑、缓存和失败日志。
- 支持不同 GPU 上执行相同实验规范。
- 能独立保存所有有效和无效实验结果。

优先适配一个小型 Triton GEMM，随后支持以插件方式接入 TileLang 或其他实现。

注意：不要试图将所有 Hopper 特有配置强行加到普通 Triton 算子上。

必须提供 Mock Runner。没有 GPU 时也能完整测试上层算法。

### 3. 离线搜索算法竞技场

实现统一 Searcher 接口：

输入：硬件、shape、配置空间、历史实验记录、剩余预算。

输出：下一批应当测试的候选配置。

至少实现：

- Random Search
- Grid / Heuristic Search
- Local Search
- 一个简单的代理模型引导搜索算法
- 复用历史硬件配置的 Transfer Baseline

建立 Offline Replay 环境，允许在已有完整或部分性能数据上模拟搜索过程。

记录每个算法在预算 B = 8、16、32、64、128 等条件下：

- 最终找到的配置性能
- 相对于已知最佳配置的 regret
- 真实评估次数
- 实际测量成本（如果可用）
- 不同随机种子的方差
- 达到指定性能比例所需的搜索预算

必须严格防止算法访问其尚未测量的配置性能，不允许拿测试数据调参。

### 4. AI 策略生成与评估框架

这是重要研究方向。

设计可供 AI Agent 调用的 Policy 接口：

A. `select_config(hardware, op, shape)`：直接预测一个或多个配置，不需要新硬件实测。

B. `search_config(hardware, op, shape, history, budget)`：根据历史信息与有限实验预算，自动选择下一次测量，并返回最终推荐配置。

策略允许实现为 Python 函数、启发式规则、决策树或轻量预测模型。

提供：

- 可运行的策略样例。
- 策略合法性检查与安全回退。
- 独立于策略生成过程的自动评分器。
- 策略版本记录与实验日志。
- 训练集、验证集、测试集隔离。
- 在未见过的 shape 和 GPU 上评估的接口。
- 供后续 AI Agent 自动生成、修改、测试策略代码的标准契约。

先实现基础设施与非 LLM baseline，不需要立即接入收费 API，也不要将特定 AI SDK 硬编码进研究框架。

### 5. L3 有限变体选择求解器

形式化如下问题：

给定 Shape 分布 D、候选 Config 集合 C，以及各个 Shape–Config 对应的真实性能矩阵 L，选出不超过 K 个配置组成集合 S，并为每个 Shape 分配 S 中的一个配置，使加权期望延迟最小。

实现：

- Oracle 参考求解（小规模可以穷举或使用数学优化器）。
- Greedy Selection
- Greedy + Local Swap
- 基于聚类或分桶的选择 baseline
- 低开销 Shape Dispatcher
- K–Loss 曲线输出

至少覆盖 K = 1、2、4、8、16。

将性能矩阵不完整作为未来扩展点，提供 Missing Measurement 的表示，不允许将预测值误标为真实值。

### 6. 分析报告工具

从数据库自动生成：

- 配置性能热力图。
- 不同搜索方法的 Regret–Budget 曲线。
- 不同 GPU 之间的配置迁移性能矩阵。
- 各配置维度的性能敏感性分析。
- L3 的 K–Loss 曲线。
- 实验失败率与测量覆盖率统计。

输出 Markdown 报告与 PNG / SVG 图像，数据不足的指标应明确标注。

### 7. 公开数据适配

研究是否可以导入公开 GPU autotuning benchmark 数据，例如 AutoTuningAssociation/benchmark_hub、Kernel Tuner 数据。

优先实现一个真实数据适配器；如果获取失败，留下完整接口与明确说明。

模拟数据只能用于测试，绝不能作为真实实验结果汇报。

## 二、工程质量要求

1. 采用 Python，必要时使用 PyTorch / Triton、NumPy、pandas、scikit-learn、pytest 等。
2. 接口与数据模型先行，各模块可以由多个 Agent 并行开发。
3. 对核心目标函数、搜索预算、调度合法性和数据隔离编写单元测试。
4. 提供统一 CLI 和最小端到端 Demo。
5. 对随机搜索、模型训练、实验回放提供随机种子。
6. 不强制安装重型编译框架才能运行纯 CPU 测试。
7. 不修改现有项目核心代码，除非确有必要。
8. 不在代码、日志和提交中保存私有连接凭据。
9. 不将未测量的配置当成已验证结果。
10. 所有暂时无法实现的功能明确标记为未完成，不要用空函数假装交付。

## 三、优先级与时间约束

可使用多 Agent 并行开发，但必须尽快冻结共享接口。

最高优先级：

- 统一数据模型
- Mock Runner + 一个真实 Kernel Adapter
- Search Arena
- L3 Solver
- 完整端到端测试

其次：

- Policy Factory
- 分析报告
- 公开数据适配

如时间不足，优先保证核心链路能真正运行，不要大量创建只有函数签名的占位工程。

不要在前期陷入大规模真实 GPU 搜索。GPU 不可用时，继续完成所有纯 CPU 模块。

## 四、交付与验收

最终至少应具备：

1. 可安装、可测试的代码仓库。
2. README、ARCHITECTURE、实验协议和接口说明。
3. 一条可执行的 Mock 数据端到端命令。
4. 一条可执行的真实 GPU 小规模测试命令（GPU 可用时执行）。
5. 一份自动生成的实验报告示例。
6. 能显示多种搜索算法比较结果。
7. 能求解一个小规模 L3 问题，并与精确最优解对照。
8. 独立的测试集，不会被搜索算法读取。
9. 当前功能、未完成功能、后续研究建议的清晰记录。
