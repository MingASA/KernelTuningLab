# 底层可靠性与实际执行边界

平台的结论必须能从记录追溯到具体源码、输入、配置、执行协议和证据。当前改进聚焦这条链路，不开发 Web UI。验收命令仍使用公开的 `check`、`run` 和 `proposal-suite`。

## 正确性贯穿完整调用

资产 Kernel 的输入默认只读，输出必须使用独立的可变容器或 Tensor 存储。输出与输入别名会被拒绝，避免输出毒化检查破坏原始输入。原地算子尚需独立的输入/输出变异契约，不应按当前只读契约接入。

平台对输入做完整指纹核对，检查构建、初始调用及计时后的输入完整性。Python 输入采用流式处理；CUDA Tensor 使用有界字节块，不复制整个输入到 CPU，也不将输入传输时间加入 Kernel 的延迟样本。检查消耗仍计入实验的实际墙钟预算。

初始正确性检查覆盖重复的完整调用。每个计时样本前，平台在计时外毒化输出并同步，避免 Kernel 跳过执行时复用之前的正确输出。warmup 和测量后，再检查**最后一次实际计时调用留下的输出**及输入指纹，不额外调用 Kernel 去掩盖状态。失败归为 `correctness_error`，该次 runtime samples 清空，不能进入成功配置排序。输出重置及其同步消耗计入总墙钟预算；该检查并不证明每一个中间计时样本都正确。

声明正确性仅跳过声明范围内的数值对比；结构、有限值及输入完整性仍需检查。声明来源仍为 `submitter_claim`，不会转成平台数值验证。声明范围递归冻结，提交者后续修改原始配置字典不会悄悄扩大适用范围。

算子可在 `metadata.validation_seeds` 提供非负整数输入种子，`0` 也是合法种子。验收在总尝试预算内选择不同的 `(config, seed)` 对；没有可调参数的固定 Kernel 也能检查多个种子。报告记录计划种子、实际种子和尝试对，未覆盖范围不能解释为已验证。

## 输出目录、恢复与取消

同一输出目录一次只允许一个运行者。第二个调用返回 `OutputDirectoryBusyError` 和非零退出码，不覆盖首个调用的进度、日志或完成标记。OS 文件锁随进程退出释放；POSIX worker 继承锁的文件描述符，监督进程被强制结束时仍存活的 worker 不会丢失目录所有权。锁用于本机实验目录；共享文件系统是否支持跨主机锁取决于该文件系统，不构成分布式调度功能。

父进程严格解析实验文件并保存执行快照，再启动 worker。实验文件的相对插件路径按原配置目录解析；CLI `--plugin` 文件路径按调用目录解析。原文件在执行期间被修改，不会改变已经冻结的实验配置。插件源码仍通过资产内容指纹检查；配置快照不是源码打包。

重跑时，上一轮配置、验收、试验结果和日志移到 `attempts/<run_id>/`，`run_metadata.json` 指向上一轮。`measurements.sqlite` 和 `measurements.jsonl` 保留累计测量日志；`run_summary.json` 的 `store_scope=cumulative_journal` 明确统计范围，当前执行次数另列。历史记录的 ID 仍可在累计数据库中定位。

SIGINT/SIGTERM、阶段超时和 worker 意外退出都会保留正在执行的候选证据。POSIX 上会清理该 worker 的进程组，包括 leader 已经崩溃后遗留的编译子进程。停止一个 worker 不保证复位失去响应的 GPU driver。

被终止的记录保留 `terminated_by_parent=true`，用于诊断；它不是已完成测量，不会阻止恢复时重新测试该配置。已完成的编译、数值或运行失败仍保留其失败语义。退出码 `130`/`143` 表示 SIGINT/SIGTERM 中断，`124` 表示硬超时；失败与 deferred 继续使用 `2`/`3`。

## 搜索、Replay 与迁移数据

| 记录 | 默认 Replay 行为 | 可作为已验证性能标签 |
| --- | --- | --- |
| 完成的编译/正确性/运行失败 | 揭示失败观察，保留状态与已知成本 | 否 |
| 数值验证成功 | 揭示成功观察 | 是，仍须满足数据集与协议隔离 |
| 仅提交者声明或明确未验证成功 | 默认不进入 verified oracle，原始日志保留证据 | 否 |
| 被监督进程终止的未完成尝试 | 不作为完成观察，原始日志保留诊断 | 否 |
| 缺少测量 | 仅生成 `missing` trace | 否 |

v1 和 v2 算法收到只读配置空间。候选迭代器只读取请求批量加一个元素，用于发现违反 batch 契约；不会先把无限建议流转成列表。任意耗时 Python 插件仍须通过 v2 子进程期限约束；v1 直接调用不提供完整的进程硬期限。

Transfer 默认只使用已验证训练标签，匹配算子实现、版本、参数、精度与资产指纹。同一源 case 下不同的测量协议、软件环境及 provenance 分别归一化，避免冷/热计时或不同源码被直接比较。跨硬件、跨 Shape 仍是允许研究的迁移方向，不会因此跨用另一 Kernel 的参数标签。

SQLite 在创建索引、建表或切换 WAL 前检查已有数据库版本；未知版本和非平台数据库会被拒绝，避免一次打开操作改变外部数据。密集 case 的 split 冲突检查使用覆盖索引，保持训练/验证/测试隔离而不逐次扫描此前的全部配置。

## 可复现的检查

```bash
.venv/bin/python -m pytest -q
.venv/bin/ktlab run --spec examples/extensions/cpu_gemm.json --output artifacts/hardening/cpu
# 使用同一命令重跑，观察 attempts/ 与缓存计数。
.venv/bin/ktlab proposal-suite --runtime python --output artifacts/hardening/proposal-cpu
```

回归测试包含执行后错误、输入改写、别名、固定配置多种子、声明范围、失败 Replay、候选流界限、迁移隔离、数据库非破坏打开、并发、取消、恢复及配置快照。长日志由 Luna 保存到 `artifacts/hardening-validation/`。

后续仍需在 5060 Ti 16GB、4090、H800、H200 上实际验证编译、数值、内存和延迟分布。CPU 回归不能证明 GPU 源码正确，也不能证明当前算子达到公开库性能。下一阶段优先收集目标机器证据，再改进测量稳定性、资源预检与具体算子性能。
